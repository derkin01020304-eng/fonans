# Банковские провайдеры и выписки

## BankProvider

Интерфейс расположен в lib/integrations/banks/bank_provider.dart:

    Future<void> authorize()
    Future<List<BankAccount>> getAccounts()
    Future<BankPage> getTransactions({String? cursor})
    Future<void> disconnect()

MockBankProvider возвращает вымышленные данные с постоянными идентификаторами. Он полностью работает офлайн и пригоден для проверки пагинации/категоризации/дедупликации, но не подключается к банку.

OAuthBankProvider использует AppAuth Authorization Code + PKCE. Банковский пароль вводится в браузере банка; access/refresh token хранятся через Android Keystore-backed secure storage. Client ID публичный. Client secret, банковские сертификаты и mTLS-ключи нельзя помещать в APK.

## Нормализованный gateway

Это контракт нашего адаптера, а не утверждение о совпадении URL с API конкретного банка. Реальный адаптер должен быть авторизован банком, проверять audience/scopes, принадлежность счетов, подписи и consent. Если нужна регистрация TPP, FAPI, mTLS, отдельный договор или региональная сертификация, это выполняется при интеграции конкретного банка.

Пример конфигурации в приложении:

    id: my_bank
    name: Мой банк
    clientId: <выданный публичный ID>
    discoveryUrl: https://auth.your-bank.example/.well-known/openid-configuration
    gateway: https://your-adapter.example/v1/
    scopes: accounts transactions

Домены .example — образцы; замените их предоставленной конфигурацией. Redirect URI по умолчанию: `app.derk.finance:/oauthredirect`. Он должен совпадать с регистрацией банка. Для production предпочтителен подтверждённый app link, если его поддерживает банк; тогда настройте AppAuth/Manifest и redirectUrl вместе.

Все суммы — целые minor units. Время передавайте RFC 3339 с часовым поясом. Поддержанные валюты: RUB, USD, EUR.

GET accounts, Authorization: Bearer TOKEN:

    {
      "accounts": [
        {
          "id": "account-123",
          "name": "Основная карта •1234",
          "currency": "RUB",
          "balanceMinor": 1000000,
          "asOf": "2026-09-07T08:00:00Z"
        }
      ]
    }

GET transactions?cursor=OPAQUE_CURSOR:

    {
      "transactions": [
        {
          "id": "immutable-bank-id",
          "accountId": "account-123",
          "signedMinor": -45050,
          "date": "2026-09-06T16:30:00Z",
          "currency": "RUB",
          "description": "Покупка",
          "merchant": "Магазин",
          "mcc": "5411",
          "kind": "expense",
          "ownAccountId": null
        }
      ],
      "nextCursor": null
    }

Первая страница передаётся без cursor. Каждая синхронизация получает все страницы доступной истории; поэтому адаптер обязан выдавать устойчивые ID и согласованный снимок счетов/истории. Незавершённые/отменённые авторизации не выдавайте как проведённые операции. Корректировки банка требуют отдельной сверки: существующий externalKey не перезаписывается автоматически.

Для собственного перевода передайте обе стороны с ownAccountId, либо одну отрицательную сторону с известным счётом назначения. Сервис создаёт канонический перевод по отрицательной стороне; положительная зеркальная запись пропускается. Межвалютный перевод требует отдельной реализации обмена и не принимается как обычный перевод.

DELETE consent должен отозвать банковское разрешение и вернуть 200 или 204. Только после успешного ответа приложение удаляет локальный OAuth-токен. Если refresh token уже недействителен, отзывите consent в кабинете банка; интеграции потребуется обработка специфичного банковского ответа.

## Баланс и повторы

Первое подключение: начальный остаток вычисляется как снимок банка минус эффект всех переданных операций. Полнота и согласованность истории — ответственность адаптера.

Повторный sync: проверка externalKey, новые проводки, обновление отдельного снимка банка. Баланс приложения продолжает вычисляться из журнала. Последующие снимки не подменяют локальный баланс и не скрывают расхождение. UI показывает локальный баланс; отдельный пользовательский экран сверки снимка пока не реализован.

BankProvider может быть реализован и без gateway, напрямую поверх официального API банка, если его условия допускают мобильного публичного клиента.

## CSV, XLSX, OFX

Пример: assets/sample_statement.csv. CSV — UTF-8, разделитель определяется по заголовку: запятая, точка с запятой или табуляция. Распознаются распространённые русские/английские названия даты, суммы, прихода/расхода, получателя, описания, MCC и ID. Сумма со знаком предпочтительна; для раздельных столбцов прихода/расхода используется соответствующий знак.

XLSX читается по первой непустой таблице и распознаваемым заголовкам. Экспорт приложения сохраняет дату текстом ISO 8601. Произвольные банковские таблицы с объединёнными заголовками, формулами и числовой датой Excel могут требовать адаптера.

OFX/QFX: базовый XML/SGML STMTTRN, FITID, DTPOSTED, TRNAMT, NAME/MEMO, CURDEF, часовой пояс OFX.

Ограничения: 10 МБ и 50 000 строк на файл. Ошибки видны в preview. Сохранение корректных новых строк требует отдельного подтверждения. Категорию и тип собственного перевода можно исправить до импорта; список раскрывается порциями по 50 строк. Если положительная входящая строка является зеркалом собственного перевода, не импортируйте её как второй перевод: используйте одну исходящую сторону.

ID выписки связывается с выбранным счётом. Без ID используется нормализованный отпечаток и порядковый номер одинакового повторения. Повтор одного файла идемпотентен; разные источники и перекрывающиеся периоды без ID не дают математической гарантии дедупликации.

PDF требует распознавания формата банка или OCR и в этом MVP не обрабатывается. Приложение сообщает об этом до записи.

## Автокатегоризация

Приоритет: подтверждённое правило пользователя по получателю → MCC → ключевые слова → «Прочее». Низкая уверенность отмечает операцию needsReview. В разделе операций есть фильтр проверки; подтверждение категории сохраняет правило для следующих импортов.
